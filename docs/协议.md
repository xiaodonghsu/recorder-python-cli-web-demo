# 录音笔 BLE 通讯协议

CB08 录音笔 ↔ 微信小程序｜协议实现与真机验证版

| **文档项** | **内容** |
| --- | --- |
| 版本  | V2.0（2026-11-01） |
| 适用项目 | record |
| 通信角色 | 小程序为 Central / 主机；录音笔为 Peripheral / 从机 |
| 依据  | 厂商《录音笔与APP通讯协议（20260313）》及 CB08 真机抓包、下载验证 |
| 验证范围 | 连接、电量、文件列表、WAV 下载、帧 CRC、字节序及文件输出结构 |

**协议结论摘要**

帧头 LEN 与 CRC 均按小端；文件列表 count/time/size 按大端；CRC 使用 CRC-16/XMODEM。文件下载命令 2-2 的完整请求帧为 36B，CB08 要求一次 GATT 写入，拆成 20+16 会稳定返回“文件不存在”。鉴权使用 TYPE=0 族的 0-50~0-55 命令，AuthKey 以 32 字节明文随帧下发，厂商协议未收录这组命令，需真机确认固件是否支持。

# 1\. 适用范围与约定

本协议用于微信小程序通过 BLE 控制 CB08 录音笔、接收实时音频、读取设备文件列表，并将设备内录音导入为 WAV 或 OPUS 文件。

多字节数值若本协议明确标注 LE，则按小端解析；文件列表结构中的整数按真机抓包结果使用 BE。除特别说明外，所有命令号均为十进制。

| **术语** | **说明** |
| --- | --- |
| App / 小程序 | BLE Central，主动扫描、连接并发送命令 |
| Dev / 录音笔 | BLE Peripheral，提供 AE20 服务并通过 Notify 回传数据 |
| LE  | Little Endian，小端；低字节在前 |
| BE  | Big Endian，大端；高字节在前 |
| GATT 单写 | 一次调用 writeBLECharacteristicValue 写入一个完整 characteristic value |

# 2\. BLE 传输层

| **对象** | **UUID** | **属性** | **方向 / 用途** |
| --- | --- | --- | --- |
| Service | 0xAE20 | Primary Service | 录音笔业务服务 |
| Characteristic | 0xAE21 | WRITE_WITHOUT_RESPONSE | App → Dev，发送协议帧 |
| Characteristic | 0xAE22 | NOTIFY | Dev → App，控制应答、音频、列表和文件数据 |
| Characteristic | 0xAE23 | NOTIFY | Dev → App，机身按键及录音状态消息 |

连接成功后必须先订阅 AE22；AE23 用于按键消息，建议同时订阅。AE22 与 AE23 应使用独立的流式帧缓存，避免两个通知特征的字节交织破坏半帧。

安卓可调用 setBLEMTU 主动协商；iOS 的 MTU 由系统固定协商。常规命令可按 MTU-3 选择载荷，但文件导入请求 2-2 按第 7 节的真机约束处理。

# 3\. 通用帧格式

| **偏移** | **长度** | **字段** | **字节序** | **取值 / 说明** |
| --- | --- | --- | --- | --- |
| 0   | 1B  | MAGIC | \-  | 固定 0x5A |
| 1   | 1B  | SEQ | \-  | 包序号，0~255 循环递增 |
| 2   | 2B  | CRC | LE  | CRC-16/XMODEM，计算范围为 LEN(2B)+DATA |
| 4   | 2B  | LEN | LE  | DATA 的真实字节数 |
| 6   | LEN | DATA | 见命令 | \[TYPE:1B\]\[CMD:1B\]\[PARAMS...\]；ACK 可仅含 TYPE |

## 3.1 CRC-16/XMODEM 参数

| **参数** | **值** |
| --- | --- |
| Polynomial | 0x1021 |
| Initial value | 0x0000 |
| RefIn / RefOut | false / false |
| XorOut | 0x0000 |
| 标准检验向量 | ASCII "123456789" → 0x31C3 |

CRC 输入必须包含帧头中的两个 LEN 原始字节，再拼接 DATA；不包含 MAGIC、SEQ 和 CRC 字段本身。

## 3.2 DATA 类型

| **TYPE** | **名称** | **内容** |
| --- | --- | --- |
| 0   | 控制命令 | 时间、电量、容量、固件、授权码 |
| 1   | 实时音频 / 转写 | 开始、音频数据、停止、暂停/继续、设备状态 |
| 2   | 文件操作 | 列表、导入、数据、结束、删除、终止 |
| 3   | 按键 / 录音控制 | 机身按键、App 控制、状态、增益 |

厂商原文第四节曾将 TYPE=3 描述为 ACK，第七节又将其定义为按键命令。实现以第七节命令表为准；若 DATA 只有一个 TYPE 字节，则按 ACK 处理。

# 4\. 控制命令（TYPE=0）

| **CMD** | **方向** | **名称** | **参数 / 应答** |
| --- | --- | --- | --- |
| 0   | App→Dev | 同步时间 | year:2B LE + month/day/hour/minute/second，各1B，共7B |
| 1   | App→Dev | 获取容量 | 无   |
| 2   | Dev→App | 容量应答 | remain:4B LE + total:4B LE；厂商原文单位标8KB，当前实现按1KB显示 |
| 3   | App→Dev | 获取电量 | 无   |
| 4   | Dev→App | 电量应答 | 1B：0~100；110 表示充电中 |
| 10  | App→Dev | 获取固件版本 | 无   |
| 11  | Dev→App | 固件版本应答 | 6B ASCII，例如 V1.0.0 |
| 12  | App→Dev | 获取授权码 | 无   |
| 13  | Dev→App | 授权码应答 | 授权码字节串 |
| 50  | App→Dev | AuthKey 认证 | authkey:32B；应答 0-51，详见 [Auth（鉴权）](#auth鉴权) |
| 52  | App→Dev | 设置新 AuthKey | authkey:32B；应答 0-53，破坏性 |
| 54  | App→Dev | 解除绑定 | 无；应答 0-55，破坏性 |

# Auth（鉴权）

本节描述 AuthKey 鉴权能力：App 把设备**当前生效**的 AuthKey（32 字节）提交给设备，设备校验后返回结果码。命令归属 TYPE=0 控制命令族，CMD 50~55。

> **适用范围提示**：AuthKey 是 pnote 系 SDK（C10 起）新增的能力，厂商《录音笔与APP通讯协议（20260313）》**未收录**这组命令——该文档的控制命令止于 CMD 13。CB08 固件是否支持必须真机确认；不支持的固件不会回 0-51，表现为**超时**而不是错误码。

## A.1 前置条件与时序

必须严格按以下顺序：

1. BLE 已连接（拿到 GATT client）
2. 已订阅 AE22 Notify（应答从 AE22 回来）
3. AE21 可写
4. 发送 0-50
5. **收到 0-51 且结果码为 0** → 认证通过
6. 之后才允许执行需要鉴权的 TYPE=1 / TYPE=2 命令

未连接就发 0-50 的后果：Android 官方 SDK 不报错，写入被**静默丢弃**，既无应答也无错误回调。所以连接状态检查与超时判定必须由 App 自己做，不能依赖协议层。

## A.2 AuthKey 格式与本地校验

| **项** | **规则** |
| --- | --- |
| 长度 | 恰好 64 位十六进制字符 = 32 字节 |
| 字符集 | `0-9` `A-F` `a-f`，大小写不敏感 |
| 前缀 | 允许 `0x` / `0X`，**不计入** 64 位长度 |
| 空白 | 允许首尾空白；内部空白非法 |
| 取值来源 | 设备**当前生效**的 AuthKey，不是 MAC，也不是 0-13 授权码 |

本地校验五步，任一步失败即抛错，**不得发出指令**：

1. `trim()`
2. 正则全匹配 `^(?:0[xX])?[0-9A-Fa-f]{64}$`
3. 若长度为 66，丢弃前 2 字节（`0x` / `0X`）
4. hex → 32 字节
5. 长度断言 == 32

Python 实现：

```python
import re

AUTHKEY_LEN = 32
_AUTHKEY_RE = re.compile(r"^(?:0[xX])?[0-9A-Fa-f]{64}$")


def encode_authkey(text: str) -> bytes:
    """把 64 位十六进制 AuthKey 字符串转成 32 字节；非法输入抛 ValueError。"""
    if text is None:
        raise ValueError("AuthKey 不能为空")
    s = text.strip()
    if not _AUTHKEY_RE.match(s):
        raise ValueError("AuthKey 必须为 64 位十六进制字符串，可带 0x 前缀")
    if len(s) == 66:
        s = s[2:]
    key = bytes.fromhex(s)
    if len(key) != AUTHKEY_LEN:
        raise ValueError("AuthKey 必须为 32 字节")
    return key
```

JavaScript 实现（小程序 / Web 控制台）：

```javascript
const AUTHKEY_RE = /^(?:0[xX])?[0-9A-Fa-f]{64}$/;

function encodeAuthkey(text) {
  const s = String(text ?? "").trim();
  if (!AUTHKEY_RE.test(s)) throw new Error("AuthKey 必须为 64 位十六进制字符串，可带 0x 前缀");
  const hex = s.length === 66 ? s.slice(2) : s;
  const out = new Uint8Array(32);
  for (let i = 0; i < 32; i++) out[i] = parseInt(hex.substr(i * 2, 2), 16);
  return out;
}
```

> AuthKey 只能由用户在 App 端输入，或经受控渠道下发；不要写进小程序包、网页 JS、APK 资源或配置文件。参见 A.9。

## A.3 命令表

| **CMD** | **方向** | **名称** | **参数** | **应答** |
| --- | --- | --- | --- | --- |
| 50 | App→Dev | AuthKey 认证 | authkey:32B | 0-51 |
| 51 | Dev→App | 认证应答 | 1B 结果码 | |
| 52 | App→Dev | 设置新 AuthKey | authkey:32B | 0-53 |
| 53 | Dev→App | 设置应答 | 1B 结果码 | |

| 55 | Dev→App | 解绑应答 | 1B 结果码 | |

**应答 CMD = 请求 CMD + 1**（50→51、52→53、54→55）。这是设备端约定，抓包时不要把 0x33 误当成请求。

## A.4 请求帧构造

payload = `[TYPE=0x00][CMD=0x32][authkey 32B]`，共 34 字节；完整帧 = 6B 帧头 + 34B = **40 字节**；LEN = `0x0022`（LE）。

帧头完全复用第 3 节：MAGIC 0x5A、SEQ、CRC-16/XMODEM、LEN，CRC 计算范围为 `LE(LEN) ‖ DATA`。

真实 TX 帧（authkey = `00112233…eeff`，SEQ=0）：

```
5A 00 A1 B8 22 00 00 32 00 11 22 33 44 55 66 77 88 99 AA BB CC DD EE FF
00 11 22 33 44 55 66 77 88 99 AA BB CC DD EE FF
```

| **片段** | **解析** |
| --- | --- |
| 5A | MAGIC |
| 00 | SEQ=0 |
| A1 B8 | CRC=0xB8A1（LE 存储） |
| 22 00 | LEN=34 |
| 00 | TYPE=0（控制命令） |
| 32 | CMD=50（AuthKey 认证） |
| 后 32B | authkey 原文 |

Python（复用 `recorder/protocol.py`）：

```python
from .protocol import build_command, TYPE_CONTROL

frame = build_command(seq, TYPE_CONTROL, 50, key32)
```

JavaScript（复用 `utils/protocol.js`）：

```javascript
const data = new Uint8Array(34);
data[0] = 0x00;   // TYPE
data[1] = 0x32;   // CMD = 50
data.set(key32, 2);
const frame = buildFrame(seq, data);
```

## A.5 应答帧解析

payload = `[0x00][0x33][result]`，LEN = 3。应答示例（result=0）：

```
5A 03 14 BE 03 00 00 33 00
│  │  └─┬─┘ └─┬─┘ │  │  └─ result = 0
│  │    │    │    │  └──── CMD = 51
│  │    │    │    └─────── TYPE = 0
│  │    │    └──────────── LEN = 3
│  │    └───────────────── CRC = 0xBE14
│  └────────────────────── SEQ = 3
└───────────────────────── MAGIC
```

`result` 就是 Android / iOS SDK 上报为 JSON `data.authkey_state` 的那个值（十进制字符串）。

> **关键**：不要用 SDK 上层 JSON 的 `"state":"0"` 判断认证成功。那个字段是回调/传输层状态，恒为 `"0"`；设备返回的认证结果在 `data.authkey_state`。iOS SDK 文档已明确此点。

## A.6 结果码

| **值** | **含义** |
| --- | --- |
| 0 | 成功 |
| 非 0 | 失败 |

非 0 的具体码值由设备固件定义，SDK 只做透传，**以设备固件协议为准**，不要臆造枚举。实现时至少要做到：把原始码值原样上报并打日志，便于现场定位；并严格区分「认证失败（收到 0-51 且 result≠0）」与「设备不支持（超时无应答）」这两种完全不同的故障。

## A.7 超时与重试

协议没有请求-应答序号回显（应答帧的 SEQ 是设备自己的计数），**只能按 (TYPE, CMD) 配对应答**，不能按 SEQ 配对。

| **场景** | **建议处理** |
| --- | --- |
| 认证超时 | 3~5 s 判超时（本仓库 `CMD_TIMEOUT = 5.0` 可直接复用） |
| 设备不支持 | 超时且重试 2~3 次仍无应答 → 判定固件不支持 AuthKey，降级为「未鉴权」工作模式 |
| 认证失败（result≠0） | 不重试。提示 AuthKey 不匹配，UI 重新输入 |
| 0-52 设置超时 | **不要直接重试**，见 A.8 |
| 0-54 解绑超时 | **不要直接重试**，见 A.8 |

## A.8 三个接口的语义与破坏性

| **命令** | **幂等** | **副作用** | **失败后果** |
| --- | --- | --- | --- |
| 0-50 认证 | 是 | 无 | 认证不通过，需鉴权的业务命令被设备拒绝 |
| 0-52 设置新 AuthKey | 语义幂等，但**不可盲目重试** | 新 AuthKey 立即生效，旧 AuthKey 失效 | 旧 AuthKey 永久失效，设备无法再用旧 key 认证 |
| 0-54 解除绑定 | 语义幂等，但**不可盲目重试** | 恢复出厂默认 AuthKey，并解除设备与 App 的绑定 | 原 AuthKey 失效；若出厂默认 key 未知，设备将无法认证 |

**重试陷阱**：0-52 / 0-54 若出现「设备已执行成功但应答丢失」，直接重试会用旧语义覆盖设备状态。可用 0-50 反向确认：

- 0-52 超时后，用 0-50 验证**旧** AuthKey 是否仍有效 → 仍有效说明设置未生效，可重试；已失效说明设置已成功，不要再发。
- 0-54 超时后，用 0-50 验证原 AuthKey 是否仍有效 → 已失效说明解绑已完成。

## A.9 安全要求

| **要求** | **说明** |
| --- | --- |
| 明文传输 | 0-50 / 0-52 的载荷就是 32 字节原始密钥，没有哈希、没有 challenge-response、没有会话密钥协商。BLE 抓包（nRF Connect / HCI dump）直接拿到密钥 |
| 传输保护 | 安全性完全依赖 BLE 链路层加密（LE Secure Connections）与配对绑定。未配对的设备上，任意主机都能抓到明文 |
| 禁止硬编码 | 不得把 AuthKey 写进小程序包、网页 JS/HTML、APK 资源、配置文件 |
| 存储 | AuthKey 属敏感凭据，移动端存 Keychain / Keystore，桌面端不要明文落盘 |
| 日志脱敏 | 不要打印完整密钥。Android 官方 SDK 在 `parseAuthkey` 成功后会把完整密钥写进日志（`[蓝牙调试][AuthKey] 转换后密钥…`），属反面例子 |
| 最小暴露 | 只在确有鉴权需求的机型/功能上启用；界面用掩码显示已录入的 key |

代码骨架（`recorder/device.py`）：

```python
    async def authkey_connect(self, authkey: str,
                              timeout: float = CMD_TIMEOUT) -> int:
        """0-50/0-51 AuthKey 认证，返回设备结果码（0=成功）。"""
        key = P.encode_authkey(authkey)
        frame = await self._request(P.TYPE_CONTROL, P.CTRL_AUTHKEY_CONNECT,
                                    key, P.CTRL_AUTHKEY_CONNECT_RESP,
                                    timeout=timeout)
        return frame.body[0] if frame.body else -1

    async def authkey_reset(self, authkey: str,
                            timeout: float = CMD_TIMEOUT) -> int:
        """0-52/0-53 设置新 AuthKey（破坏性：旧 key 立即失效）。"""
        key = P.encode_authkey(authkey)
        frame = await self._request(P.TYPE_CONTROL, P.CTRL_AUTHKEY_RESET,
                                    key, P.CTRL_AUTHKEY_RESET_RESP,
                                    timeout=timeout)
        return frame.body[0] if frame.body else -1

    async def authkey_unbond(self, timeout: float = CMD_TIMEOUT) -> int:
        """0-54/0-55 解除绑定并恢复出厂 AuthKey（破坏性）。"""
        frame = await self._request(P.TYPE_CONTROL, P.CTRL_AUTHKEY_UNBOND,
                                    b"", P.CTRL_AUTHKEY_UNBOND_RESP,
                                    timeout=timeout)
        return frame.body[0] if frame.body else -1
```

> `Frame.body` 是 TYPE、CMD 之后的字节；对 0-51 而言 `body[0]` 即结果码。

## A.11 验收清单

| **检查项** | **通过标准** |
| --- | --- |
| 帧构造 | 0-50 的 TX 帧为 40 字节，`LEN=0x0022`，CRC 与 `crc16_xmodem` 结果一致 |
| 短 key | 传入 63 位或 65 位 hex → 本地抛错，**不产生任何 TX 帧** |
| 非 hex | 传入含 `g-z` 的字符串 → 本地抛错，不发帧 |
| 前缀容错 | `0x` + 64 位与裸 64 位产生**完全相同**的帧 |
| 应答解析 | 收到 0-51 能取出结果码；`result=0` 判成功，`result≠0` 判失败并上报原始码值 |
| 时序 | 未连接时调用不阻塞、不误判成功；超时后按「设备不支持」降级 |
| 幂等 | 连续发两次 0-50，两次都收到 0-51，设备状态不变 |
| 破坏性 | 0-52 / 0-54 在 UI 上有二次确认；真机验证后原 AuthKey 行为符合预期 |
| 安全 | 日志与界面均不出现完整 AuthKey |

## A.12 与 0-12 / 0-13「授权码」的区别

两者名字相近但完全不是一回事，不要混用：

| **维度** | **0-12 / 0-13 授权码** | **0-50 AuthKey 认证** |
| --- | --- | --- |
| 方向 | App 读设备标识 | App 向设备提交密钥 |
| 语义 | 单向下行查询，拿到设备出厂标识 / 授权码字符串 | 双向校验，设备确认「你持有正确密钥」 |
| 参数与应答 | 请求无参，应答为字节串 | 请求携带 32 字节密钥，应答为 1 字节结果码 |
| 是否鉴权 | 否 | 是 |
| 设备支持 | CB08 厂商协议已收录 | 厂商协议未收录，需真机确认 |

关于 0-12/0-13 究竟是「授权码」还是「MAC」，见 `docs/协议差异对照.md` C4：厂商 docx 写的是「获取 mac / 回复 `s+Mac`」，本 md 与厂商测试页 `docs/vendor_page/app.js:249` 写的是「授权码」，**待厂商确认**。

# 5\. 实时音频命令（TYPE=1）

| **CMD** | **方向** | **名称** | **参数 / 应答** |
| --- | --- | --- | --- |
| 0   | App→Dev | 开始实时转写 | 无   |
| 0   | Dev→App | 本次录音文件名 | 设备在开始推流前发送文件名 |

# 7\. 文件列表与下载流程

## 7.1 文件列表结构（CMD 2-1）

| **字段** | **长度** | **字节序** | **说明** |
| --- | --- | --- | --- |
| count | 4B  | BE  | 本帧包含的文件条目数，不是全部文件总数 |
| time | 4B  | BE  | 录音时长，单位秒；个别固件可能使用绝对时间戳 |
| size | 4B  | BE  | 设备内压缩文件大小，单位 Byte |
| name | 25B | UTF-8/ASCII | 固定长度、NUL填充；长文件名会截断扩展名 |

设备可用多帧 CMD=1 发送列表。App 应累积每一帧的 N 条记录，收到 CMD=18 后交付完整列表；为兼容不发送 CMD=18 的旧固件，可在最后一帧后空闲约1.2秒进行 best-effort 收尾。

典型文件名 note 2026-10-31-16-41-04.opus 长29B，而列表字段只有20B，因此列表实际返回 note 2026-10-31-16-41-04.。下载时必须重建完整扩展名。

## 7.2 普通下载请求（CMD 2-2）

| **参数** | **长度** | **字节序** | **示例** |
| --- | --- | --- | --- |
| offset | 4B  | LE  | 首次下载为 00 00 00 00 |
| filename | 25B | ASCII/UTF-8 | note 2026-10-31-16-41-04.wav + 00 |

**强制约束｜2-2 必须整帧单写**

完整协议帧为 36B。CB08 真机 A/B 已确认：一次 GATT write 写入36B可成功；若在应用层拆为20B+16B，设备会把文件名解析错误并返回 CMD=5 / code=1（文件不存在）。不要让通用分包器拆分2-2帧。

**步骤 1｜读取真实 MTU**

连接后可调用 getBLEMTU 获取 ATT_MTU，常规命令的单次载荷为 MTU-3。2-2 仍按上述强制约束整帧发送。

**步骤 2｜重建目标文件名**

优先使用 base.wav，让录音笔转码输出标准 WAV；失败时可尝试 base.opus 和列表原始截断名。filename 字段固定24B，不足补0。

**步骤 3｜发送完整请求**

构造 TYPE=2、CMD=2、offset=0 和24B文件名，连同6B通用帧头一次写入 AE21。

**步骤 4｜接收文件数据**

收到 CMD=3 后建立会话；持续拼接 CMD=4 的 body 字节；每次有效数据可刷新空闲超时。

**步骤 5｜处理结束码**

收到 CMD=5：code=0 时写盘；code=1 时换候选名；code=2 时重置 offset；code=3 或传输中断时停止并提示。

# 程序控制录音卡

本节给出**由 App 主动控制录音卡开始录音、暂停录音、继续录音、结束录音**的完整实现指引，含可执行代码。

> **先分清两件事**：设备上有**两套互不相同**的录音相关命令族，名字都带「录音」，但用途完全不同，选错会导致功能不生效或状态混乱。
>
> | | **TYPE=3 录音控制族**（本节主体） | **TYPE=1 实时音频族**（本节末对照） |
> | --- | --- | --- |
> | 作用 | 控制**录音卡本体**录制，音频**存进设备存储**，事后可下载成文件 | 控制**实时音频码流**从设备推流到 App，用于边听边转写 |
> | 命令 | 3-1 / 3-3 / 3-5 / 3-7 | 1-0 / 1-2 / 1-3 |
> | 有无应答 | **有**，结果码 1=成功 2=失败 | **无**应答，靠 1-4 设备状态与 1-0 文件名通告感知 |
> | 产物 | 设备内录音文件 | App 侧实时音频流 |
> | 典型场景 | 「会议录音」按钮 → 设备录完整文件 → 下班后下载归档 | 「边录边转写」→ 实时上云做 ASR |
>
> **一句话判断**：要「录下来以后再取」用 TYPE=3；要「现在就在手机上听/转写」用 TYPE=1。两者**互不替代**，可同时使用。

## B.1 前置条件与时序

| **前置项** | **要求** |
| --- | --- |
| BLE 连接 | 已连接，且 AE22 已订阅（AE23 建议同时订阅） |
| 鉴权 | 若固件启用 AuthKey，必须先完成 0-50 认证并收到 result=0，否则录音控制命令可能被拒 |
| 发送通道 | 全部经 AE21（WRITE_WITHOUT_RESPONSE）单写发出 |
| 应答通道 | 从 AE22 收回；AE23 是机身按键事件，不承载本节命令的应答 |

标准时序：

```
App                                   设备
 │  3-1  开始录音  ────────────────────►│
 │ ◄──────────────────── 3-2  result=1 │  成功
 │                                      │
 │  3-5  暂停录音  ────────────────────►│
 │ ◄──────────────────── 3-6  result=1 │
 │                                      │
 │  3-7  继续录音  ────────────────────►│
 │ ◄──────────────────── 3-8  result=1 │
 │                                      │
 │  3-3  保存录音  ────────────────────►│
 │ ◄──────────────────── 3-4  result=1 │  文件已落盘
 │                                      │
 │  3-19 查询状态   ────────────────────►│
 │ ◄──────────────────── 3-20  state=1  │  1录音中 2未录音 3暂停
```

**要点**：每个命令都必须等**自己那一条**应答回来再发下一条。3-1/3-3/3-5/3-7 的应答分别是 3-2/3-4/3-6/3-8，不要按「请求 CMD+1」的通则去配对——虽然数值上确实相邻，但**必须按语义写死映射表**，因为同一族里 19/21/23/25/27 这些查询命令的应答是 20/22/24/26/28，且 3-1 与 3-2 是「请求/结果」而非「请求/数据」。

## B.2 命令表与应答码

| **请求 CMD** | **名称** | **应答 CMD** | **应答参数** | **成功值** |
| --- | --- | --- | --- | --- |
| 1 | 开始录音 | 2 | 1B 结果码 | 1=成功，2=失败 |
| 3 | 保存录音 | 4 | 1B 结果码 | 1=成功，2=失败 |
| 5 | 暂停录音 | 6 | 1B 结果码 | 1=成功，2=失败 |
| 7 | 继续录音 | 8 | 1B 结果码 | 1=成功，2=失败 |
| 19 | 获取录音状态 | 20 | 1B 状态 | 1=录音中，2=未录音，3=暂停 |
| 21 | 获取录音时间 | 22 | duration:2B LE + currentSize:4B LE | — |
| 23 | 获取当前文件名 | 24 | 文件名字节串 | — |
| 25 | 获取增益 | 26 | 1B | 1=低，2=中，3=高 |
| 27 | 设置增益 | 28 | 1B 结果码 | 0=成功，1=失败 |

> **状态码两套不要混**：录音控制的**结果码**是 1/2（1 成功），而**设置增益的结果码**是 0/1（0 成功）。判断成功请**分别处理**，不要用同一个 `=== 0` 或 `=== 1` 的通用判断。

**顺序约束**：

- 3-5（暂停）只在**录音中**有效；未录音时设备返回 3-6 result=2。
- 3-7（继续）只在**暂停态**有效；未暂停时设备返回 3-8 result=2。
- 3-3（保存）的作用是**结束本次录音并落盘**。保存后再发 3-3 无意义。
- 3-1（开始）在**已录音或已暂停**时再发，会返回 3-2 result=2。

## B.3 请求帧构造

请求帧沿用第 3 节的通用帧格式，`DATA` = `[TYPE=0x03][CMD][PARAMS...]`，控制命令无参数。

```python
def build_frame(seq: int, type_: int, cmd: int, params: bytes = b"") -> bytes:
    """第 3 节通用帧。CRC-16/XMODEM，覆盖 LEN(2B)+DATA，小端。"""
    data = bytes([type_, cmd]) + params
    crc = crc16_xmodem(len(data).to_bytes(2, "little") + data)
    return bytes([0x5A, seq & 0xFF]) + crc.to_bytes(2, "little") \
        + len(data).to_bytes(2, "little") + data
```

四条控制命令的完整帧（SEQ=0 起，LEN=2）：

```
开始录音  3-1   5A 00 1A A8 02 00 03 01
暂停录音  3-5   5A 01 9E E8 02 00 03 05
继续录音  3-7   5A 02 DC C8 02 00 03 07
保存录音  3-3   5A 03 58 88 02 00 03 03
```

帧头解剖（以开始录音为例）：

```
5A 00 1A A8 02 00 03 01
│  │  └─┬─┘ └─┬─┘ └──── DATA (2B) ────┘
│  │    │    └── LEN = 0x0002
│  │    └─────── CRC = 0xA81A（小端：crcLo=0x1A, crcHi=0xA8）
│  └──────────── SEQ = 0
└─────────────── MAGIC = 0x5A
```

`DATA` 只有 2 字节：`03` 是 TYPE=3，`01` 是 CMD。

## B.4 应答帧解析

设备应答同为通用帧，`DATA` = `[TYPE=0x03][CMD][RESULT:1B]`。

```
设备应答（开始录音成功）  5A 01 xx xx 03 00 03 02 01
                                        └─┬─┘ └───┬─┘
                                          TYPE  CMD=2  result=1
```

解析要点：

1. 按 **LEN** 重组，可能跨多个 Notify。
2. 校验 CRC，不通过则丢弃并记录原始 hex。
3. 取 `DATA[0]` 确认 TYPE==3，再取 `DATA[1]` 得到应答 CMD，按 B.2 的**语义映射表**分发。
4. `DATA[2]` 即结果码，空应答体要当作异常处理，不要默认成功。

**不要**用「请求 CMD+1」硬算应答 CMD。虽然本节这几条恰好相邻，但 3-19→3-20、3-21→3-22 等查询同样相邻，一旦协议增补命令就会错位。维护一张显式的 `CMD → RESP_CMD` 字典更稳妥。

### B.5.5 业务层：加锁的录音会话

直接照搬四个方法连续调用，会遇到「用户连点两次开始」这类竞态。业务层务必加状态锁。

```python
import asyncio

class RecordSession:
    """示例：封装「开始 → 暂停/继续 → 保存」为一个受控会话。"""

    def __init__(self, device):
        self.dev = device
        self._lock = asyncio.Lock()
        self._state = 0          # 0未录音 1录音中 2暂停 3已保存

    async def start(self) -> bool:
        async with self._lock:
            if self._state in (1, 2):
                raise RuntimeError("已在录音中，请先保存")
            r = await self.dev.record_start()
            if r != 1:
                return False
            self._state = 1
            return True

    async def pause(self) -> bool:
        async with self._lock:
            if self._state != 1:
                return False          # 非录音态，忽略
            return await self._pause_locked()

    async def resume(self) -> bool:
        async with self._lock:
            if self._state != 2:
                return False          # 非暂停态，忽略
            return await self._resume_locked()

    async def save(self) -> bool:
        async with self._lock:
            if self._state not in (1, 2):
                return False
            r = await self.dev.record_save()
            if r != 1:
                return False
            self._state = 3
            return True

    async def toggle_pause(self) -> bool:
        """UI 上的一个「暂停/继续」按钮。

        复用 pause() / resume()，它们各自已做状态校验；
        不要重复实现命令下发逻辑。
        """
        async with self._lock:
            if self._state == 1:
                return await self._pause_locked()
            if self._state == 2:
                return await self._resume_locked()
            return False

    async def _pause_locked(self) -> bool:
        """已在锁内执行暂停。"""
        r = await self.dev.record_pause()
        if r != 1:
            return False
        self._state = 2
        return True

    async def _resume_locked(self) -> bool:
        """已在锁内执行继续。"""
        r = await self.dev.record_resume()
        if r != 1:
            return False
        self._state = 1
        return True
```

### B.5.6 小程序侧调用示例

> 以下为**示意代码**：`sendKeyRequest` / `queryRecordState` 需自行按 B.3 的组帧规则与 B.4 的解析规则实现。本仓库 `recorder/device.py` 已提供完整的 Python 实现（`record_start` / `record_pause` / `record_resume` / `record_save` / `record_state`），小程序或 Web 端可参照移植。

```javascript

async function startRecord() {

  } else {
    wx.showToast({ title: '开始录音失败', icon: 'none' });
  }
}

// 小程序：暂停 / 继续 切换
async function togglePause() {
  const state = await queryRecordState();    // 3-19 → 3-20
  if (state === 1) {                          // 录音中 → 暂停
    await sendKeyRequest(3, 5, 6);
  } else if (state === 3) {                   // 暂停 → 继续
    await sendKeyRequest(3, 7, 8);
  }
}

// 小程序：结束录音（保存）

  }
}
```

## B.6 与 TYPE=1 实时音频族的区别（对照）

TYPE=1 的 1-0/1-2/1-3 经常被误当成录音控制，**它们控制的是实时码流推流，不是设备落盘录音**。

| **动作** | **TYPE=3 录音控制（本节）** | **TYPE=1 实时音频** |
| --- | --- | --- |
| 开始 | 3-1，payload `03 01` | 1-0，payload `01 00` |
| 暂停 | 3-5，payload `03 05` | 1-3，payload `01 03 01` |
| 继续 | 3-7，payload `03 07` | 1-3，payload `01 03 00` |
| 结束 | 3-3，payload `03 03` | 1-2，payload `01 02` |
| 应答 | 有，3-2/3-6/3-8/3-4 带结果码 | 无；设备另发 1-0 文件名、1-4 状态 |
| 音频去向 | 设备存储，事后按第 7 节下载 | 设备经 AE22 推流，App 侧收 OPUS 码流 |

**TYPE=1 暂停/继续的特别说明**：1-3 的**同一个 CMD** 用参数区分两种动作——`1B：0=继续，1=暂停`。所以暂停和继续的 payload 只差最后一字节：

```
暂停  01 03 01
继续  01 03 00
```

这是最容易写错的地方：把 `0` 和 `1` 写反，表现是「点了暂停反而继续了」，且不报错。

**TYPE=1 的额外代价**：开始后设备会先发一条 1-0 通告**本次录音文件名**，再开始推 1-1 音频数据；App 必须先收下文件名才能把码流存成正确的文件。TYPE=3 则没有这一步。

## B.7 常见问题排查

| **现象** | **原因与处理** |
| --- | --- |
| 发 3-1 无任何应答 | 检查 AE22 是否订阅成功；检查是否已完成 AuthKey 认证；固件可能不支持 TYPE=3 |
| 应答回来但结果码是 2 | 状态不对：非录音态发暂停、非暂停态发继续、已录音态再发开始。先用 3-19 查状态再决定 |
| 暂停后设备仍在写文件 | 3-5 返回 2，说明未处于录音态；先确认 3-1 已成功 |
| 保存后找不到文件 | 3-3 成功后按第 7 节用 2-0 拉列表；列表里名字可能被截断到 20B（见 7.1） |
| 暂停/继续行为反了 | TYPE=1 的 1-3 参数写反：0=继续、1=暂停；TYPE=3 的 3-5/3-7 是两条独立命令，不存在此问题 |
| 误把 3-1 当成 TYPE=1 的 1-0 | 二者语义不同，见 B.6。落盘录音用 3-1，实时推流用 1-0 |
| 连点按钮导致状态错乱 | 业务层加锁，见 B.5.5 |
| 应答 CMD 对不上 | 不要用「请求+1」推算，用显式映射表，见 B.4 |

## B.8 验收清单

| **检查项** | **通过标准** |
| --- | --- |
| 开始录音 | 发 3-1，收到 3-2 且 result=1 |
| 暂停录音 | 发 3-5，收到 3-6 且 result=1；随后 3-19 返回 3=暂停 |
| 继续录音 | 发 3-7，收到 3-8 且 result=1；随后 3-19 返回 1=录音中 |
| 结束录音 | 发 3-3，收到 3-4 且 result=1；随后 2-0 列表中出现新文件 |
| 状态查询 | 3-19 → 3-20 的值在 1/2/3 之间且与实际操作一致 |
| 文件名 | 3-23 → 3-24 返回的名字与 2-0 列表中的条目一致 |
| 非法顺序 | 录音态下重复发 3-1，设备应回 result=2，App 不应崩溃 |
| 断连 | 录音中断开时 App 不得停留在「录音中」假状态 |

# 9\. 解析、超时与兼容策略

| **场景** | **建议处理** |
| --- | --- |
| BLE Notify 分片 | 按 LEN 跨通知重组；一个通知可能含半帧，也可能含多帧 |
| AE22 / AE23 并发 | 使用独立 FrameParser 缓冲，解析后统一分发 |
| CRC错误 | 已锁定端序后丢弃损坏帧并记录原始hex |
| 端序未知 | 连接后用电量查询探测 LEN/CRC 组合，CRC命中即锁定 |
| 列表无 CMD=18 | 收到数据后空闲约1.2秒，返回已累积列表 |
| 文件下载无数据 | 空闲约12秒判定超时；若 received=0 可换候选名 |
| 传输中断且已有数据 | 不要自动换文件名；提示失败或使用 offset 续传 |
| 主动取消 | 发送 CMD=7，清理定时器和 Promise，忽略取消类弹窗 |
| 同名文件 | 本地缓存路径加入 time/size/序号，避免覆盖 |
| 鉴权无应答 | 0-50 超时 3~5 s；重试 2~3 次仍无应答 → 判定固件不支持 AuthKey，降级为未鉴权模式 |
| 鉴权失败码 | 收到 0-51 且 result≠0 表示 AuthKey 不匹配，不重试，交由用户重新输入 |
| 破坏性命令超时 | 0-52 / 0-54 超时后不要直接重试，先用 0-50 反查当前 AuthKey 是否仍有效 |
